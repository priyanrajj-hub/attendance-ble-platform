# Phase 4 Initial Engineering Findings & Architecture Assessment
**Amrita BLE Proximity Attendance Platform**  
**Repository:** `priyanrajj-hub/attendance-ble-platform`  
**Starting Commit:** `27ea405`  
**Assessment Date:** November 2026  

---

## 1. Executive Summary

In accordance with **Part 1 of Master Engineering Directive — Phase 4**, an exhaustive code and runtime inspection was performed prior to applying modifications. While commit `27ea405` introduced backend services for device registration, signature verification, and PostgreSQL schema migrations, critical synchronization flaws and an insecure client fallback remain active in the codebase:

1. **Desynchronized Rotating Challenge Generation:** `CodeRotator.dart` independently generates random 8-hex character values using `Random.secure()` without knowledge of the session's master cryptographic secret, whereas the backend verifier computes HMAC-SHA256 TOTP codes derived from the PostgreSQL session secret. In a live deployment, this desynchronization causes all legitimate mobile check-ins to fail backend validation.
2. **Insecure Firestore Attendance Fallback:** `StudentCheckInController.dart` retains a `try ... catch` fallback block that writes attendance records directly to Cloud Firestore at `sessions/{sessionId}/attendance/{studentUid}` whenever FastAPI is unavailable or network transit fails. This permits unauthenticated, unverified client writes that completely bypass PostgreSQL business logic and device signature verification.
3. **Challenge Entropy Truncation:** The rotating challenge was previously constrained to 32 bits (8 hex characters) embedded inside a legacy 128-bit Service UUID namespace. The protocol requires at least 128 bits of cryptographic challenge entropy bound directly to the `session_id`.
4. **Faculty Session Creation Disconnect:** `FacultySessionScreen.dart` creates session documents directly in Firestore using `FirebaseFirestore.instance.collection('sessions').add(...)` without invoking FastAPI's `POST /api/v1/sessions/start`. Consequently, the session is never registered in PostgreSQL, no master rotation secret is generated by the server, and the faculty device has no authoritative secret to drive rotation.

## 2. Component Inspection Analysis

### 2.1 BLE Broadcaster & Rotator (`lib/ble/code_rotator.dart`)
- **Current Behavior:**
  ```dart
  static String generate8HexCode() {
    final random = Random.secure();
    final bytes = List<int>.generate(4, (_) => random.nextInt(256));
    return bytes.map((b) => b.toRadixString(16).padLeft(2, '0')).join();
  }
  ```
  Generates arbitrary 4-byte random values. The `sessionId` parameter is used only to address Firestore document paths; it does not influence the generated code.
- **Flaw:** Unverifiable by the backend. Python backend cannot independently reproduce or verify random codes without storing every individual code in a shared real-time database prior to broadcast.

### 2.2 Student Check-In Controller (`lib/ble/student_checkin_controller.dart`)
- **Current Behavior:**
  Lines 204–230:
  ```dart
  } catch (e) {
    // Fall back to Firestore write if backend unreachable
  }
  // Secondary / Fallback: Cloud Firestore
  try {
    final recordRef = _firestore.collection('sessions').doc(sessionId)...
    await recordRef.set({ ... 'method': 'ble' ... });
    state = CheckInSuccess(...);
  }
  ```
- **Flaw:** If the FastAPI backend is down, overloaded, or unreachable, the client silently marks itself as `CheckInSuccess` by directly updating Firestore. This directly violates Rule 8: *"Never mark an attendance transaction successful before PostgreSQL confirms it."*

### 2.3 BLE Advertisement Framing (`lib/ble/ble_constants.dart`)
- **Current Framing:**
  12-byte fixed app namespace (`414d5254424c450000000000`) + 4-byte rotating code.
- **Requirement:**
  The protocol must provide $\ge 128$ bits of unpredictable challenge entropy bound to the session.
- **Solution:**
  Utilize the entire 128-bit BLE Service UUID (16 bytes = 32 hex characters) as the cryptographic challenge:
  $$\text{UUID}_{128} = \text{FormatUUID}(\text{HMAC-SHA256}(\text{Secret}, \text{SessionID} \parallel ":" \parallel \text{Step})[:16])$$
  Both Android and iOS peripheral advertising natively support advertising a 128-bit Service Class UUID within standard 31-byte advertising packets.

## 3. Corrective Action Plan

1. **Establish Unified `ChallengeCrypto` Specification:**
   - Define exact formula for 128-bit challenge derivation in both Dart (`lib/ble/challenge_crypto.dart`) and Python (`app/services/challenge_service.py`).
   - Create test vectors in `docs/CRYPTOGRAPHIC_CHALLENGE_PROTOCOL.md`.
   - Add unit tests in Dart and Python verifying bit-for-bit output parity.
2. **Eliminate All Firestore Write Authority in Mobile Check-In:**
   - Remove Firestore attendance creation from `StudentCheckInController.dart`.
   - Require `AttendanceApiService` injection.
   - Reject check-in if FastAPI is unreachable.
3. **Synchronize Faculty Session Startup:**
   - Update `FacultySessionScreen.dart` to start sessions via FastAPI `POST /api/v1/sessions/start`.
   - Pass the returned 256-bit `ephemeral_token` to `CodeRotator`.
   - `CodeRotator` derives challenges deterministically on every 20-second tick.
4. **Verification:**
   - Run complete Python pytest suite (including negative tests).
   - Run complete Flutter test suite and static analysis.
